# MeshChat code audit and compatibility notes

## Scope and evidence

The reference is original `liamcottle/reticulum-meshchat` commit `df5aea94eab7f4be1cdfef494446e9d6979aed77`, whose `package.json` reports 2.4.0. The contract covers the entire application interface, not just the initial text-chat subset. All 52 route declarations in `meshchat.py` are represented: 49 REST operations, two WebSocket handshakes and `/`. The `public/` static mount is recorded separately. HTTP GET registrations also create library-managed HEAD handlers; these are annotated rather than counted as separate application declarations.

The audit reads the backend route handlers, serializers, configuration mutations, persistence definitions, WebSocket dispatcher/emitters, audio forwarding, NomadNet download handling, frontend HTTP call sites, WebSocket connection helper and audio protobuf definition. No MeshChat instance or Rust daemon was started. See `validation-report.json` for the checks actually executed, the source-file hashes, literal response branches and frontend call-site inventory.

RNS/LXMF transport-interface examples under `src/backend/interfaces/` are not imported by the application entry point and are not extra MeshChat application endpoints. CLI identity-generation commands and Electron IPC are likewise outside the requested HTTP/WebSocket interface.

## HTTP contract details

**Origin and hosting.** Default binding is `127.0.0.1:8000`. The frontend derives both WebSocket URLs from its page origin. The backend serves the built `public/` tree after API routes, including `call.html` and audio assets. It is not a generic SPA fallback. [`meshchat.py` 2056–2063, 3596–3602; `WebSocketConnection.js` 35–50](https://github.com/liamcottle/reticulum-meshchat/blob/df5aea94eab7f4be1cdfef494446e9d6979aed77/src/frontend/js/WebSocketConnection.js#L35-L50)

**Status codes and errors.** Successful REST calls use 200, including sends and mutations. Explicit errors normally contain `{"message":"..."}`. Invalid JSON, missing nested fields, invalid hexadecimal strings and conversion errors can escape as native HTTP errors, often 500 text/plain. The specifications do not invent a universal error envelope. Interface import/export catches differ from other handlers; their descriptions preserve those exceptions. [`meshchat.py` 776–901, 1771–1834](https://github.com/liamcottle/reticulum-meshchat/blob/df5aea94eab7f4be1cdfef494446e9d6979aed77/meshchat.py#L776-L901)

**Size limits.** HTTP request bodies and the control WebSocket have an explicit 50 MiB (52,428,800-byte) limit. A base64 attachment consumes more JSON-body space than its raw bytes. The audio socket uses the installed aiohttp default, and forwarding is constrained by the installed RNS `Link.MDU`; neither is assigned an invented fixed value here. [`meshchat.py` 904–911, 2056–2063; `audio_call_manager.py` 44–56](https://github.com/liamcottle/reticulum-meshchat/blob/df5aea94eab7f4be1cdfef494446e9d6979aed77/src/backend/audio_call_manager.py#L44-L56)

**Mutating GET requests.** Announcing, initiating/hanging up calls, propagation sync/stop and marking conversations read use GET. Optional path requests and ping also cause network activity. Preserve existing verbs at the compatibility boundary. Do not run automatic crawlers or indiscriminate HEAD probes against these routes. [`meshchat.py` 1030–1196, 1343–1367, 2031–2042](https://github.com/liamcottle/reticulum-meshchat/blob/df5aea94eab7f4be1cdfef494446e9d6979aed77/meshchat.py#L1030-L1196)

**Configuration.** GET returns all 21 keys. PATCH and `config.set` handle the same 13 writable keys. Unsupported keys are ignored. Interval updates also set automatic-announcement enablement. Boolean setters use Python truth conversion, so the string `"false"` is not the same as JSON `false`. Integer coercion and partial writes can fail without rollback. Full config is broadcast after a successful update, including an empty update. Empty display name/theme is ignored; null restores defaults by removing stored values. [`meshchat.py` 2097–2172, 2376–2399](https://github.com/liamcottle/reticulum-meshchat/blob/df5aea94eab7f4be1cdfef494446e9d6979aed77/meshchat.py#L2097-L2172)

**Interface editing.** These endpoints write Reticulum configuration and do not reload active interfaces. Type-specific required settings are encoded as conditional JSON Schemas. Unknown type names are accepted upstream. Optional fields processed by `InterfaceEditor` are removed when absent, null or empty, so overwrite is not JSON Merge Patch. Multi-interface GET responses flatten child sections into `sub_interfaces`; import-preview keeps raw named sections. [`meshchat.py` 329–359, 427–901; `interface_editor.py` 1–14](https://github.com/liamcottle/reticulum-meshchat/blob/df5aea94eab7f4be1cdfef494446e9d6979aed77/src/backend/interface_editor.py#L1-L14)

**Paths and discovery.** An unknown path returns 200 with `path:null`, not 404. Only exact query strings `request=true` and `request=1` enable discovery/waiting. Announcements are ordered newest-first by database update time. Ping's numeric RTT is in seconds even though its human-readable message displays milliseconds. [`meshchat.py` 1199–1237, 1432–1483, 1567–1653](https://github.com/liamcottle/reticulum-meshchat/blob/df5aea94eab7f4be1cdfef494446e9d6979aed77/meshchat.py#L1432-L1483)

**Dependency-owned responses.** Interface statistics and path-table entries originate in the installed RNS package. MeshChat transforms selected bytes to hex but otherwise returns those objects. Its dependency declarations use lower bounds, not exact versions. Those schemas are deliberately open: claiming a complete fixed field list from this repository alone would be unsupported. Propagation's last-transfer result similarly passes through without local type enforcement. [`meshchat.py` 1332–1340, 1718–1768; `requirements.txt`](https://github.com/liamcottle/reticulum-meshchat/blob/df5aea94eab7f4be1cdfef494446e9d6979aed77/meshchat.py#L1718-L1768)

## Messaging and persistence

**Live and stored messages differ.** Send responses and created/state events serialize a 16-field live object. History, cancel responses and incoming-delivery events use the 19-field stored object, including `id`, `created_at` and `updated_at`. The stored `method` can be null in migrated rows. Database timestamps are strings whose source does not guarantee RFC 3339 formatting; they are not declared `format: date-time`. [`meshchat.py` 2446–2524, 2645–2667; `database.py` 110–137](https://github.com/liamcottle/reticulum-meshchat/blob/df5aea94eab7f4be1cdfef494446e9d6979aed77/meshchat.py#L2645-L2667)

**Send semantics.** POST send returns after routing/queueing, not after delivery. The created event can arrive before the HTTP response. No idempotency key is accepted. Only `image`, `audio` and `file_attachments` are mapped through named JSON fields; binary data is base64. A title input is not consumed. Explicit direct/opportunistic/propagated methods are recognized; other strings fall back to automatic selection. [`meshchat.py` 1771–1834, 2886–3008](https://github.com/liamcottle/reticulum-meshchat/blob/df5aea94eab7f4be1cdfef494446e9d6979aed77/meshchat.py#L2886-L3008)

**Delivery states.** Full state updates appear through callbacks and a one-second loop, so duplicate updates are possible. The loop stops on delivered, failed, rejected, cancelled, or sent with propagated method. The latter is not proof of receipt by the final recipient. Message progress is percentage-scaled; NomadNet progress is not. Incoming messages should be identified with `is_incoming`, not treated as outbound delivery receipts. [`meshchat.py` 2527–2564, 3011–3039](https://github.com/liamcottle/reticulum-meshchat/blob/df5aea94eab7f4be1cdfef494446e9d6979aed77/meshchat.py#L3011-L3039)

**History and deletion.** History is ordered by database id, with exclusive `after_id`; asc selects larger ids, every other order string selects smaller ids. There is no total-count/cursor envelope. REST deletion removes database rows without cancelling sends or emitting deletion events. An in-flight send can recreate a deleted row. `lxmf_message_deleted` is used specifically when automatic resend removes the old failed message. Read state is local and has no remote receipt. [`meshchat.py` 1885–2042, 3109–3168](https://github.com/liamcottle/reticulum-meshchat/blob/df5aea94eab7f4be1cdfef494446e9d6979aed77/meshchat.py#L1885-L2042)

## WebSocket rules

**Control socket.** All messages on `/ws` are UTF-8 JSON text. New connections cause a config broadcast to every connected control client, not only the newcomer. Ping/pong and NomadNet results are request-local; other events are broadcast. There are no subscriptions, event IDs, sequence numbers, acknowledgement envelopes or replay cursors. Unknown/malformed commands are generally logged without a reply. The supplied browser pings every 30 seconds and reconnects one second after close. Recovery requires REST reads. [`meshchat.py` 904–938, 2206–2373; `WebSocketConnection.js`](https://github.com/liamcottle/reticulum-meshchat/blob/df5aea94eab7f4be1cdfef494446e9d6979aed77/meshchat.py#L2206-L2373)

**NomadNet.** File/page download replies are progress, success or failure variants. Correlation uses destination hash plus the original path, with no independent request identifier. Concurrent identical requests are ambiguous. `field_data` is a required page-command key; send `{}` when unused. Backtick path variables become `var_` fields, while form fields become `field_` fields. Progress is the raw RNS fraction, normally 0–1. [`meshchat.py` 2179–2351, 3437–3517](https://github.com/liamcottle/reticulum-meshchat/blob/df5aea94eab7f4be1cdfef494446e9d6979aed77/meshchat.py#L2179-L2351)

**Audio socket.** `/api/v1/calls/{audio_call_link_hash}/audio` is a separate binary WebSocket. The backend forwards opaque packet bytes; the frontend uses proto2 `AudioCallPayload`, containing `AudioData` and Codec2 mode/data. Closing the socket is not a call hangup. The JSON protocol descriptor records every protobuf field and enum without misrepresenting audio as JSON. [`audio_call.proto`; `CallPage.vue` 370–479](https://github.com/liamcottle/reticulum-meshchat/blob/df5aea94eab7f4be1cdfef494446e9d6979aed77/src/frontend/public/assets/proto/audio_call.proto#L1-L31)

## Defects to separate from desired Rust behavior

These are source observations, not requirements to reproduce bugs. The favourite-delete success text incorrectly says the favourite was added. Audio socket cleanup registers the listener again instead of unregistering it. Clearing inactive calls mutates the list being iterated and may skip adjacent entries. Replacing RNodeMultiInterface child sections deletes dictionary entries during iteration and can raise an error. Local propagation enablement errors can be swallowed while the configuration reports the requested setting. Each is marked in the specifications or the cited handlers. [`meshchat.py` 643–649, 1017–1027, 1160, 1319–1329, 263–271](https://github.com/liamcottle/reticulum-meshchat/blob/df5aea94eab7f4be1cdfef494446e9d6979aed77/meshchat.py#L1101-L1162)

## Security boundary

The source has no application authentication, authorization, explicit Origin allowlist or per-client access partition. Connected clients share the same identity, configuration and stored messages. Interface mutation includes options such as PipeInterface command configuration. The default loopback binding matters. A remotely reachable Rust endpoint should have an explicit access policy and limits. That would be an intentional extension and must not be described as existing MeshChat behavior. No claim of an exploitable vulnerability or penetration-test result is made here. [`meshchat.py` 427–773, 904–938, 2056–2063, 3596–3602](https://github.com/liamcottle/reticulum-meshchat/blob/df5aea94eab7f4be1cdfef494446e9d6979aed77/meshchat.py#L2056-L2063)

## Bounded adoption proposal for LXMF-rs

Keep these complete reference specifications under the existing repository's documentation. A first implementation can expose config/app-info, discovery, conversation/history/send/cancel/read state and their control events, using existing daemon services. The unchanged application shell also polls calls and propagation status; a text-chat implementation must make an explicit decision about those requests rather than assume they never occur. Keep remaining functions visibly unsupported or implement them, rather than return fabricated state. Do not start a second chat application.

Treat any Rust-friendly API design, stricter validation, authentication, replay, transactional settings or corrected response text as a deliberate extension or separate native API. Do not silently rewrite the compatibility contract. Test the final binding with a pinned frontend build and a Python reference peer before claiming interoperability. This proposal is not part of the extracted upstream contract.
