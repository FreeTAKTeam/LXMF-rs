# Upgrade to v0.14.0

Update public LXMF-rs package versions together to 0.14.0. The patched ZeroMQ
dependency is published as `reticulum-rs-zeromq`; its Rust library name remains
`zeromq`. Consumers using LXMF-rs workspace aliases need no import changes.

Use Rust 1.88 or newer. The previous 1.85 declaration was incompatible with
the locked `time` and ICU dependencies; v0.14.0 declares and checks 1.88.

## Rust envelope construction

Add `response_connection_id: None` to direct `ZmqRpcEnvelope` struct literals.
Prefer the existing `ZmqRpcEnvelope::request` and `::response` constructors when
possible. The SDK manages the generation for its own PUSH/PULL response socket;
custom clients must rotate it when replacing that socket. The generation is a
routing discriminator, not an authenticated identity.

Existing protocol-v1 clients and non-ZeroMQ SDK flows remain supported.
An uncertain mutation result still requires reconciliation; do not infer that
a transport failure means the daemon did not execute it.

## Optional durable custody

Normal upgrades do not enable the durable broker automatically. Enabling it
requires persistent local storage and explicit capability negotiation. Before
enabling `--zmq-durable-broker`, stop writers and take SQLite-consistent backups
of the daemon database and any paired consumer state, identities, and settings.
Choose a sufficient initial database budget; reopening does not silently resize
the persisted budget. A full store deliberately rejects new admission.

Follow the [operations runbook](../goals/zmq-rch-durable-broker/OPERATIONS.md)
for migration/backfill, custody versus delivery, consumer checkpoints, explicit
backup-restore incarnation, and downgrade. Do not run old binaries against a
migrated store. A rollback requires an agreed consistent pre-cutover backup and
accounting for admitted work. Network side effects cannot be undone by restoring
a database.
